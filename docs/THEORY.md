## 1. Протоколи SOAP, REST, MQTT

### 1.1 SOAP (Simple Object Access Protocol)

- XML-based протокол обміну повідомленнями, зазвичай поверх HTTP (але специфікація
  дозволяє й SMTP, JMS тощо — прив'язки до транспорту немає).
- Структура конверта: `Envelope` → `Header` (опційно: метадані, WS-Addressing,
  WS-Security токени) → `Body` (корисне навантаження **або** `Fault`).
- Контракт **завжди формальний**: WSDL описує операції, XSD — типи даних. Клієнт і
  сервер генерують код із того самого контракту (contract-first) — звідси сильна
  типізація і менше "сюрпризів" у продакшені.
- Стилі: RPC vs Document; encoding: literal vs encoded. У сучасних enterprise-системах
  майже завжди **Document/Literal (wrapped)** — саме так побудований `soap-service`.
- Обробка помилок — стандартизований `<soap:Fault>` (faultcode/faultstring/detail),
  а не довільний HTTP-статус.
- Розширюваність через WS-\*: WS-Security (підпис/шифрування частин повідомлення),
  WS-ReliableMessaging (гарантована доставка), WS-Addressing (асинхронна
  маршрутизація), WS-AtomicTransaction (розподілені транзакції).
- **Де в проєкті:** `soap-service` — contract-first сервіс на Spring-WS.
  XSD (`common-model/src/main/resources/xsd/order.xsd`) — єдине джерело істини,
  WSDL генерується автоматично (`WebServiceConfig`), помилки — через
  `@SoapFault`-анотований `OrderNotFoundException`.

**Питання на співбесіді:** *"Чому SOAP досі використовують у enterprise, попри
складність порівняно з REST?"*
→ Формальний, машинно-перевірюваний контракт (XSD/WSDL) знижує ризик несумісності
між командами/системами; стандартизовані WS-\* розширення закривають безпеку,
надійність доставки і транзакційність "з коробки"; глибока сумісність зі старими
корпоративними системами (SAP, банкінг, держсектор, страхування), де SOAP — де-факто
стандарт десятиліттями.

### 1.2 REST (Representational State Transfer)

- Це **архітектурний стиль** (Roy Fielding, 2000), не протокол і не стандарт.
- Обмеження (constraints): client-server, **stateless** (кожен запит самодостатній),
  cacheable, **uniform interface** (ресурси ідентифікуються URI, маніпулюються через
  представлення — JSON/XML, повідомлення самоописові, HATEOAS), layered system,
  code-on-demand (опційно).
- HTTP-дієслова відображають CRUD: `GET` (читання, safe+idempotent), `POST`
  (створення, НЕ ідемпотентний), `PUT` (повна заміна, idempotent), `PATCH`
  (частковий апдейт), `DELETE` (idempotent).
- Коди відповіді несуть семантику: 2xx — успіх, 4xx — помилка клієнта (400 невалідні
  дані, 401 не автентифікований, 403 немає прав, 404 не знайдено), 5xx — помилка сервера.
- Richardson Maturity Model: рівень 0 (один endpoint, POX) → 1 (ресурси) → 2 (дієслова
  + статус-коди — де перебуває більшість реальних "REST" API) → 3 (HATEOAS — рідкість).
- **Де в проєкті:** `rest-service` — `/api/{basic|oauth|mtls}/orders`, стандартні
  дієслова й статус-коди (200/201/400/401/403/404), stateless (кожен запит несе свої
  креденшели/токен).

### 1.3 MQTT (Message Queuing Telemetry Transport)

- Легкий **publish/subscribe** протокол поверх TCP (або WebSocket), спроєктований
  для обмежених мереж/пристроїв (IoT): мінімальний бінарний заголовок (2 байти
  мінімум), низьке споживання трафіку/батареї.
- Архітектура через **брокер**: видавці (publishers) і споживачі (subscribers) не
  знають один одного напряму — брокер маршрутизує повідомлення за **топіком**
  (ієрархія через `/`, wildcard `+` — один рівень, `#` — всі рівні нижче).
- **QoS-рівні** — ключова відмінність від REST/SOAP, де такого вибору немає:
  - QoS 0 — at most once (fire-and-forget, можлива втрата);
  - QoS 1 — at least once (гарантована доставка, можливі дублікати → споживач має
    бути ідемпотентним);
  - QoS 2 — exactly once (4-way handshake, найдорожче).
- **Retained message** — брокер зберігає останнє повідомлення топіка й одразу віддає
  його новому підписнику (корисно для стану "останній відомий статус").
- **Last Will and Testament (LWT)** — повідомлення, яке брокер сам опублікує, якщо
  клієнт відключиться "брудно" (без DISCONNECT) — типовий механізм presence/heartbeat
  у інтеграціях.
- **Persistent session** (`cleanSession=false`) — брокер зберігає підписки й чергу
  повідомлень, поки клієнт офлайн.
- **Де в проєкті:** `mqtt-integration` — вбудований брокер Moquette
  (`EmbeddedMqttBroker`), `OrderEventPublisher`/`OrderEventSubscriber` на Eclipse
  Paho, топік `integration/orders/events`, QoS 1.

**Питання на співбесіді:** *"Коли MQTT доречніший за REST/SOAP?"*
→ Коли інтеграція асинхронна й слабо зв'язана (publisher не має чекати на
consumer), коли одну подію мають отримати кілька незалежних споживачів
(fan-out), коли мережа нестабільна/дорога (IoT, мобільні канали), у
event-driven архітектурах ("сталася подія" замість "виконай операцію зараз").

## 2. XML, XSD, WSDL, JSON, JSON Schema

- **XML** — деревоподібна розмітка з підтримкою namespace; документ може бути
  *well-formed* (синтаксично коректний) і/або *valid* (відповідає схемі).
- **XSD (XML Schema Definition)** — типізація й обмеження для XML: `simpleType`
  (з `restriction`/`enumeration`/`pattern`), `complexType`, `targetNamespace`,
  `elementFormDefault`. У contract-first підході XSD — єдине джерело істини:
  з нього генерують і Java-класи (JAXB/xjc), і WSDL.
- **WSDL (Web Services Description Language)** — контракт SOAP-сервісу: `types`
  (вбудовує/імпортує XSD), `message`, `portType` (операції), `binding`
  (протокол/кодування), `service` (адреса endpoint). WSDL 1.1 (класичний,
  найпоширеніший) vs 2.0.
- **JSON** — легкий формат обміну даними без схеми "з коробки": object / array /
  string / number / boolean / null.
- **JSON Schema** — контракт для JSON (аналог XSD у світі REST): ключові слова
  `type`, `required`, `properties`, `additionalProperties`, `enum`, `format`,
  `pattern`, `$ref`, `oneOf`/`anyOf`/`allOf`. Версії (drafts): draft-07,
  2019-09, 2020-12.
- **Де в проєкті:** `common-model` містить **одну канонічну модель у двох
  представленнях**:
  - `src/main/resources/xsd/order.xsd` — контракт для SOAP (з нього
    `jaxb2-maven-plugin`/xjc генерує Java-класи `xml.generated.*`, а Spring-WS
    у `soap-service` автоматично будує з нього WSDL);
  - `src/main/resources/json-schema/order-schema.json` — контракт для REST
    (`additionalProperties: false` — тобто зайві поля відхиляються, так само як
    XSD не пропустить невідомий елемент);
  - `mapper/OrderMapper` — "Message Translator" між JAXB-об'єктом і POJO;
  - `validation/JsonSchemaValidator` — обгортка над `networknt/json-schema-validator`,
    якою `rest-service` валідує вхідний JSON **до** десеріалізації (та сама роль,
    що XSD-валідація виконує для SOAP).

## 3. Механізми автентифікації: Basic, mTLS, OAuth2

### 3.1 HTTP Basic (RFC 7617)

- Заголовок `Authorization: Basic base64(user:pass)` надсилається **на кожен
  запит**. Base64 — це кодування, **не шифрування**, тому Basic Auth осмислений
  лише поверх TLS.
- Немає токенів, немає expiry, немає scope — сервер або довіряє
  логін/пароль, або ні. Просто впровадити, легко скомпрометувати
  (креденшели передаються постійно; логи/proxy можуть їх "побачити", якщо TLS
  термінується завчасно).
- **Де в проєкті:** `soap-service` (`SoapSecurityConfig`) і `rest-service`
  (`/api/basic/**` у `SecurityConfig`).

### 3.2 mTLS (Mutual TLS)

- У звичайному TLS автентифікується **тільки сервер** (клієнт перевіряє
  сертифікат сервера). У mTLS **обидві сторони** пред'являють X.509-сертифікат
  під час TLS-handshake.
- Спрощений handshake: `ClientHello` → `ServerHello` + сертифікат сервера →
  (опційно) `CertificateRequest` → клієнт надсилає свій сертифікат +
  `CertificateVerify` (доказ володіння приватним ключем) → `Finished` з обох
  боків.
- Потребує PKI: CA, ланцюг довіри, **keystore** (моя власна ідентичність:
  приватний ключ + сертифікат) і **truststore** (кому я довіряю — зазвичай
  сертифікат CA, а не конкретні leaf-сертифікати).
- `client-auth`: `need` (обов'язково) vs `want` (запитується, але з'єднання не
  рветься за відсутності — рішення "обов'язково чи ні" тоді ухвалює вже рівень
  застосунку).
- Типовий вибір для machine-to-machine інтеграцій у zero-trust/enterprise
  ландшафтах (нема "людини", яка вводить пароль; ідентичність прив'язана до
  самого TLS-з'єднання, а не до токена, який можна вкрасти й використати з
  іншої машини).
- **Де в проєкті:** `rest-service` — окремий Tomcat-конектор
  (`MtlsConnectorConfig`, `client-auth=want`) на порту 8444, Spring Security
  `x509()` (`SecurityConfig.mtlsChain`) мапить CN сертифіката на принципала;
  `certs/generate-certs.sh` генерує весь ланцюг (root CA → server/client certs
  → keystore/truststore).

### 3.3 OAuth2 / JWT

- OAuth2 — фреймворк **авторизації** (не автентифікації!): дозволяє клієнту
  отримати обмежений доступ до ресурсу від імені власника ресурсу **без**
  передачі пароля цьому клієнту.
- Ролі: Resource Owner, Client, Authorization Server (видає токени), Resource
  Server (перевіряє токени й віддає дані).
- Grant types: Authorization Code (+PKCE) — для застосунків з користувачем
  у браузері; **Client Credentials** — типовий вибір для system-to-system
  інтеграцій (без людини в циклі, саме це демонструє проєкт); Refresh Token —
  подовження життя без повторного логіну.
- **JWT**: `header.payload.signature` (base64url), claims: `iss`, `sub`, `aud`,
  `exp`, `iat`, `scope`. Resource Server перевіряє підпис через публічний ключ
  (JWKS endpoint), а потім `exp`/`aud`/`iss` і `scope` для авторизації дій.
- OIDC (OpenID Connect) — надбудова над OAuth2, що додає ідентифікацію
  (`id_token`, `/userinfo`) — OAuth2 сам по собі про автентифікацію користувача
  нічого не каже.
- **Де в проєкті:** `rest-service` — `/api/oauth/**`. `AuthTokenController`
  (навчальний mock Authorization Server у стилі Client Credentials) видає
  RS256-підписаний JWT; `JwkSetController` публікує публічний ключ як JWKS;
  Spring Security `oauth2ResourceServer().jwt()` перевіряє підпис і вимагає
  конкретний `SCOPE_orders.read`/`SCOPE_orders.write` залежно від операції.

**Питання на співбесіді:**
- *"Чим OAuth2 краще за Basic для інтеграцій?"* → токени з обмеженим часом
  життя й конкретним scope, немає постійної передачі пароля, токен можна
  відкликати не змінюючи креденшели клієнта, підтримка різних grant-типів під
  різні сценарії (людина / сервіс).
- *"Чим mTLS сильніший за bearer-токен?"* → ідентичність прив'язана до самого
  TLS-з'єднання й доводиться володінням приватним ключем при кожному
  handshake; вкрадений bearer-токен можна використати з будь-якої машини, а
  вкрадений сертифікат без приватного ключа — марний.

## 4. Адміністрування TLS/SSL сертифікатів

- **X.509-сертифікат**: subject (кому виданий), issuer (хто видав), термін дії,
  публічний ключ, розширення (SAN — subjectAltName, keyUsage,
  extendedKeyUsage), підпис видавця.
- **Ланцюг довіри**: root CA (самопідписаний, довіра встановлюється поза
  протоколом — "out of band") → (опційно intermediate CA) → leaf-сертифікат.
- **Життєвий цикл видачі**: згенерувати keypair → сформувати CSR (Certificate
  Signing Request, підписаний власним приватним ключем як доказ володіння) →
  CA підписує CSR своїм приватним ключем → отримуємо сертифікат.
- **Keystore vs Truststore** — постійне джерело плутанини на співбесідах:
  - keystore = **моя ідентичність** (приватний ключ + мій сертифікат) —
    пред'являю іншій стороні;
  - truststore = **кому я довіряю** (зазвичай сертифікат CA, а не конкретні
    leaf-сертифікати — так додавання нового клієнта не вимагає змін
    truststore, доки він підписаний тим самим CA).
- **Формати**: PEM (текст, base64, `-----BEGIN CERTIFICATE-----`), PKCS12/`.p12`
  (бінарний, з паролем, може містити ключ+сертифікат+ланцюг в одному файлі —
  сучасний стандарт для Java), JKS (застарілий Java-специфічний формат).
- **Інструменти**: `openssl` (кросплатформний, CSR/підпис/конвертація
  форматів), `keytool` (частина JDK, керує Java keystore/truststore).
- **Експлуатаційна відповідальність**: моніторинг терміну дії (протермінований
  сертифікат — класичний інцидент інтеграції рівня L3: "все раптом перестало
  працювати о півночі"), ротація/оновлення, відкликання (CRL, OCSP).
- **TLS 1.2 vs 1.3**: 1.3 — коротший handshake (менше round-trip), суворіший
  набір cipher suites; практична деталь, з якою реально зіткнулись у цьому
  проєкті — JSSE (Java TLS-реалізація) не підтримує post-handshake
  authentication, тому "опційний" клієнтський сертифікат (`client-auth=want`)
  за TLS 1.3 поводиться інакше, ніж за 1.2 (є попередження в логах
  `rest-service` під час старту з `MTLS_ENABLED=true`) — гарний приклад
  "теорія раптом стала практичною проблемою".
- **Де в проєкті:** `certs/generate-certs.sh` — повний скрипт: root CA → server
  cert (CN=localhost, SAN) → client cert (CN=integration-client) → PKCS12
  keystore/truststore для сервера й клієнта. Детальніше — `certs/README.md`.

## 5. Cross Domain Solution (CDS)

- **Що це:** механізм (програмний або апаратний), що контролює й гарантує
  безпечний обмін даними між доменами з різним рівнем довіри/класифікації
  (наприклад: інтернет ↔ корпоративна мережа, DMZ ↔ внутрішній контур,
  unclassified ↔ classified у держ./defense-секторі, OT ↔ IT на виробництві).
  У SAP-контексті — межа між внутрішньою SAP-системою і зовнішніми
  партнерами/хмарними сервісами.
- **Ключові гарантії, які CDS зобов'язаний забезпечити:**
  1. **Контентна фільтрація / whitelisting** — пропускається лише те, що
     відповідає суворому контракту; усе, чого немає в контракті, автоматично
     відкидається (звужує поверхню атаки — невідоме поле не може "протягнути"
     ін'єкцію чи прихований payload).
  2. **Аудит-трейл** — кожне перетинання межі домену обов'язково логується
     (хто, що, коли, дозволено/відхилено) — вимога для комплаєнсу/розслідування
     інцидентів.
  3. **Fail-closed за замовчуванням** — будь-яке порушення контракту зупиняє
     повідомлення **до** того, як воно потрапить у внутрішній домен, а не
     "пропускаємо й розберемось пізніше".
  4. (У найсуворіших реалізаціях) — фізична однонаправленість потоку даних
     ("data diode") — апаратна гарантія, що дані можуть текти лише в один бік.
- **Де в проєкті:** `integration-hub` →
  `processor/CrossDomainGuardProcessor` — перед тим, як Content-Based Router
  дозволить повідомленню рухатись далі у внутрішні канали (SOAP/REST/MQTT),
  процесор:
  - валідує вхідний JSON проти `order-schema.json`
    (`additionalProperties:false` = whitelist полів — те саме, що робить
    справжній CDS на рівні контенту);
  - пише структурований аудит-запис (`CDS_AUDIT` logger) з рішенням
    `CDS_ALLOW`/`CDS_DENY`;
  - **fail-closed**: при порушенні кидає `CrossDomainViolationException`, і
    Camel-маршрут зупиняється — повідомлення НЕ потрапляє до
    SOAP/REST/MQTT-каналів.

**Питання на співбесіді:** *"Як CDS відрізняється від звичайного firewall?"*
→ Firewall фільтрує на мережевому/транспортному рівні (IP, порт, іноді
протокол). CDS працює на **рівні контенту повідомлення** — розуміє формат
(XML/JSON), перевіряє його проти бізнес-контракту, і додає гарантії
аудиту/односпрямованості, які звичайний firewall не надає.

## 6. Enterprise Service Bus (ESB) та Service Oriented Architecture (SOA)

### 6.1 SOA

- Архітектурний **стиль**: система будується як набір слабозв'язаних
  (loosely coupled), перевикористовуваних **сервісів** зі стандартизованим,
  платформонезалежним контрактом (WSDL/XSD або REST API-опис).
- Принципи (за Erl): формальний контракт, слабка зв'язаність, абстракція
  (реалізація прихована за контрактом), перевикористовуваність, автономність,
  statelessness, discoverability, композиційність (сервіси можна комбінувати
  в бізнес-процеси).
- **Мета:** уникнути "point-to-point spaghetti integration" — коли N систем
  напряму інтегровані одна з одною (до N² з'єднань, кожне зі своїм форматом),
  і звести все до стандартизованих контрактів через спільну шину.

### 6.2 ESB

- **Інфраструктурний компонент**, що реалізує SOA на практиці: центральний
  "хребет" для маршрутизації, трансформації й оркестрації повідомлень між
  системами.
- Типові функції: **routing** (content-based — за вмістом повідомлення,
  itinerary-based — за заданим маршрутом), **transformation/mapping**
  (XML↔JSON, схема A → схема B), **protocol bridging** (SOAP↔REST↔MQTT↔файл↔БД
  через адаптери), **orchestration**, **monitoring/logging**, централізоване
  **enforcement безпеки**.
- Класичні патерни інтеграції (Enterprise Integration Patterns, Hohpe &
  Woolf), які ESB реалізує: **Message Router**, **Content-Based Router**,
  **Message Translator**, **Channel Adapter**, **Canonical Data Model**,
  Aggregator, Splitter.
- Компроміс: централізація = менше "хаосу", але і потенційний bottleneck/
  single point of failure; сучасна альтернатива — decentralized/event-driven
  інтеграція ("smart endpoints, dumb pipes", за Мартіном Фаулером) через
  мікросервіси й брокери подій.
- Технології: Apache Camel, MuleSoft, IBM Integration Bus, TIBCO
  BusinessWorks, Talend — і, що важливо для цієї вакансії, **SAP PI/PO — це і
  є ESB SAP-стеку** (див. розділ 7).
- **Де в проєкті:** `integration-hub` (Apache Camel) — саме "міні-ESB":
  - єдина точка входу `POST /hub/orders` (і `direct:hub-inbound-order` для
    внутрішньої/тестової оркестрації);
  - **Content-Based Router** — `choice()/when(header("channel")...)` у
    `IntegrationHubRoutes` вирішує, у який канал піде повідомлення;
  - **Message Translator** — `JsonToXmlOrderTranslator` (JSON → XML
    `createOrderRequest`) на гілці SOAP;
  - **Channel Adapters** — `SoapChannelGateway` / `RestChannelGateway` /
    `MqttChannelGateway` (кожен інкапсулює специфіку свого протоколу);
  - **Canonical Data Model** — та сама модель `Order`, що описана в
    `order.xsd`/`order-schema.json`, є спільним "мовним стандартом" для всіх
    трьох каналів.

**Питання на співбесіді:**
- *"У чому різниця SOA і ESB?"* → SOA — архітектурний стиль/принцип; ESB —
  один із можливих технічних засобів його реалізації (SOA можлива й без ESB,
  наприклад через API Gateway + мікросервіси).
- *"Чому в 2020-х ESB вважають дещо застарілим підходом?"* → тренд до
  мікросервісів/event-driven/decentralized інтеграції, ESB може ставати
  bottleneck і "God object", логіка розмазується по XML-конфігураціях, важко
  тестувати й версіонувати. Але в enterprise/SAP-ландшафтах (банкінг,
  держсектор, великі виробництва) ESB (і саме SAP PI/PO) досі є стандартом
  через регуляторні вимоги й legacy-обмеження — і саме тому ця навичка й
  досі затребувана окремою позицією.

## 7. SAP PI/PO та SAP NetWeaver AS Java (бажані навички)

Це власницькі (proprietary) технології SAP — їх не можна відтворити в pet-проєкті
буквально, тому теорія і мапінг понять на цей проєкт винесені в окремий файл:
**[docs/SAP-PI-PO-THEORY.md](./SAP-PI-PO-THEORY.md)**.
Коротко: SAP PI/PO — це промислова реалізація ESB усередині SAP-екосистеми
(Integration Directory/Repository, Communication Channels, Message Mapping,
ccBPM), а SAP NetWeaver AS Java — Java EE-подібний application server, на
якому PI/PO (у double-stack режимі) виконувався.

## 8. Java EE Application Servers (бажана навичка)

- Java EE (нині Jakarta EE) — набір специфікацій для серверної Java:
  Servlet, **JAX-WS** (SOAP), JAX-RS (REST), EJB, CDI, JPA, JMS.
- **Application server** (WildFly/JBoss, Payara/GlassFish, WebLogic,
  WebSphere, **SAP NetWeaver AS Java**) реалізує ці специфікації й надає
  контейнер: lifecycle керування бінами, dependency injection, транзакції,
  пул з'єднань до БД, безпеку — розгортається WAR/EAR-архів.
- **JAX-WS, код-фьорст стиль** (протилежність contract-first підходу через
  Spring-WS/XSD, який показаний у `soap-service`):
  ```java
  @WebService(targetNamespace = "http://petproject.integration/orders")
  public class LegacyOrderService {

      @WebMethod
      public OrderDto getOrder(@WebParam(name = "orderId") String orderId) {
          // бізнес-логіка
      }
  }
  ```
  Такий клас, розгорнутий на WildFly/Payara, **сам генерує WSDL** із анотацій
  (протилежний напрямок руху порівняно з contract-first: спочатку Java-код,
  потім контракт — на практиці менш надійно для міжкомандної інтеграції,
  оскільки контракт легко випадково "зламати" рефакторингом коду).
- **Порівняння зі Spring Boot-підходом**, який використано в цьому
  pet-проєкті (embedded Tomcat, самодостатній "fat jar", без окремого
  застосунок-сервера) — типова еволюція індустрії за останні ~10 років, і
  важливо вміти пояснити обидва підходи на співбесіді, бо в SAP-orientованих
  enterprise-командах повний перехід на Spring Boot трапляється не завжди.

## 9. Основні обов'язки — як про них говорити на співбесіді

Ці пункти з опису вакансії — не технології, а процесні/soft-skill очікування.
Швидкі "якорі" відповідей, з прив'язкою до того, що реально є в цьому проєкті:

| Обов'язок з вакансії | Як про це говорити (і що показати з проєкту) |
|---|---|
| Стабільна робота інтеграцій SAP ↔ інші системи | Поясни моніторинг/логування (`CDS_AUDIT`, structured logging в кожному сервісі), обробку помилок (SOAP Fault, JSON Schema 400, mTLS 401/403) — стабільність починається з передбачуваної поведінки під час збоїв. |
| Збір і формалізація бізнес-вимог | Канонічна модель `order.xsd`/`order-schema.json` — приклад формалізації вимог у контракт **до** написання коду (contract-first мислення). |
| Пошук технічних/процесних рішень з урахуванням архітектурних обмежень | Поясни компроміси, які зроблено в проєкті: чому mTLS на окремому конекторі, а не profile-based; чому CDS-guard — окремий крок, а не "вбудований" у кожен ендпоінт. |
| Налаштування/конфігурування системи | `application.yml` у кожному модулі — конфігурація через змінні середовища (12-factor), а не хардкод. |
| Функціональна й технічна документація | Цей `docs/THEORY.md`, `README.md`, коментарі "чому" (а не "що") в коді — стиль, який очікують від технічної документації в реальній роботі. |
| Взаємодія з командами розробки/архітекторами | Модульна структура (`common-model` як спільний контракт між командами SOAP/REST/MQTT) — ілюструє, як окремі команди можуть незалежно розвивати "свій" канал, тримаючи спільний контракт стабільним. |
| Координація тестування, контроль якості | У кожному модулі — реальні automated-тести (SOAP Fault-сценарій, JSON Schema-валідація, OAuth2 scope-перевірка, CDS-guard rejection, MQTT pub/sub round-trip). |
| Супровід впровадження, контроль після релізу | Логи з чіткими рівнями (INFO для успіху, WARN/ERROR для відхилень) у кожному сервісі — основа для post-release моніторингу. |
| Аналіз інцидентів L3 | Класичні "L3-варті" сценарії явно відтворені: протермінований/невалідний сертифікат (`certs/`), невалідне повідомлення (`400 schema_validation_failed`), відмова автентифікації (`401`/`403`), SOAP Fault. Вмій пояснити, з чого почнеш діагностику кожного. |
| Актуальність документації/інтеграційних сценаріїв | README з mapping-таблицею вимог вакансії на код — приклад підходу "документація = живий артефакт, що трасується до коду", а не окремий Word-файл, що застаріває. |
